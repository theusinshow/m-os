# M/OS v0.3 — spec-mãe

Data: 2026-08-13
Estado: aguardando revisão

Este documento define escopo, sequenciamento e decisões. Ele não descreve
implementação — isso está nas duas specs filhas.

---

## 1. Objetivo

Aplicar integralmente o design fechado em `Design System/design_handoff_frontend/`
sobre o app existente, criando no back-end o que o desenho exige e não existe, e
integrar o M/OS ao Hermes que já roda na VPS — como mais uma superfície dele, nunca
como um segundo agente.

## 2. Decomposição

| Spec | Escopo | Depende de |
|---|---|---|
| **A** | camada visual + estrutural: tokens, shell, 6 telas, overlays, motion, símbolo, e o schema que o desenho exige | nada |
| **B** | ponte com o Hermes: transporte, sessão, modo Hermes no Command | contrato em `docs/HERMES-GATEWAY-CONTRACT.md`; túnel de pé para verificação |

Ordem: **A → B**. A não toca em Hermes; B não toca em telas além do Command.

**Voz saiu do escopo.** Estava planejada como spec C e foi explicitamente adiada.
Consequência: `CaptureSource` **não** ganha a variante `voice` agora, e o rótulo
`VOZ · 14 s` do protótipo permanece o que é — conteúdo falso de demonstração.

## 3. Decisões tomadas

| # | Decisão | Consequência |
|---|---|---|
| 1 | O design manda sobre os docs de produto onde houver conflito | `CORE-FOUNDATION.md`, `PRODUCT.md` e `ROADMAP.md` são corrigidos junto, não deixados mentindo |
| 2 | Kanban tem 6 estados reais | migration de schema; `Planned` e `Review`, antes descartados, voltam |
| 3 | Rail tem 6 destinos; Settings vai ao rodapé; Workspaces só pelo Command | o README permite "rodapé ou Command" para Settings |
| 4 | GitHub entra só como campo `repository` | sem API, sem token, sem Issue — é o que a tela mostra |
| 5 | O M/OS é cliente do Hermes existente | sem provider próprio, sem chave de modelo, sem skill duplicada |
| 6 | A ponte vive fora do Core | `crates/mos-hermes`, sem dependência de `mos-storage-sqlite` |
| 7 | Sessão do M/OS é própria e persistente | separada do WhatsApp; retomada por `session.resume` |
| 8 | `approval.request` é renderizado e respondido | a conversa nunca trava esperando em silêncio |
| 9 | Raciocínio fica escondido, revelável sob demanda | resposta limpa por padrão |

## 4. Conflitos com documentação anterior

Registrados aqui para não virarem contradição silenciosa. Vão para `DECISIONS.md`.

**4.1 — O handoff proíbe mudar back-end.**
`design_handoff_frontend/README.md` afirma: *"Nenhuma chamada de `api.ts` muda de
assinatura. Nenhuma tabela muda."* O handoff foi escrito supondo que o back-end já
suportava o desenho. Ele não suporta. A instrução do proprietário do produto foi criar
o que falta. O README perde nesta questão específica e continua valendo em todo o resto.

**4.2 — `Planned` e `Review` foram excluídos de propósito.**
`CORE-FOUNDATION.md:107` justifica: *"`Planned` depende de uma semântica temporal ainda
inexistente. `Review` depende de um fluxo de trabalho que ainda precisa ser validado."*
Isso continua verdade. A decisão de incluí-los assume que **coluna de kanban é
visualização, não semântica** — um card em `planned` não promete nenhum comportamento
temporal, e `review` não dispara fluxo nenhum. Se um dia essa semântica existir, ela se
apoia em estados que já estarão persistidos. `ARCHITECTURE-REVIEW.md` recomendava
remover `Planned`; essa recomendação fica revogada e o motivo fica escrito.

**4.3 — `inbox` como estado de Task.**
`CORE-FOUNDATION.md:104` recusava o nome "para evitar colisão com a Inbox de Captures".
A colisão é real e permanece: `Task.state = "inbox"` e a Inbox de Captures são coisas
diferentes com o mesmo nome. Mitigação é nomenclatura, não renomeação — o desenho usa
`INBOX` como rótulo da coluna e mudar isso quebraria o design. Fica documentado nos dois
lugares onde alguém tropeçaria: `work.rs` e `CORE-FOUNDATION.md`.

## 5. Riscos declarados

1. **Migration 6 → 7 só anda para frente.** O risco é menor do que parece: o storage já
   chama `create_pre_migration_snapshot` (`mos-storage-sqlite/src/lib.rs:188`) antes de
   aplicar qualquer migration, e verifica a integridade do snapshot depois de gravá-lo.
   A proteção é automática e não depende de ninguém lembrar. O que resta é o de sempre:
   um banco migrado não volta a abrir numa build antiga.
2. **Tracking sai de `0` para os valores reais** em toda a tipografia. Muda a métrica de
   cada linha de texto do app; alinhamento de coluna e truncamento precisam ser
   reconferidos, não presumidos.
3. **Focus muda de `outline` para `border-color` + halo.** É o que a especificação manda,
   mas perde o offset que hoje ajuda em elemento sem borda. Se algum controle ficar com
   foco ilegível, a correção é dar borda ao controle — não reintroduzir `outline`.
4. **O contrato do Hermes foi lido do checkout local de junho/2026.** Se a VPS roda outra
   versão, nomes de método podem divergir. Mitigação em B: método desconhecido é erro de
   contrato explícito, nunca falha genérica.
5. **Com Hermes ligado, o que você digitar no Command sai da máquina.** Vai para a sua
   VPS, pelo túnel — não para terceiro. Ainda assim é saída de dado e fica dito na UI.
